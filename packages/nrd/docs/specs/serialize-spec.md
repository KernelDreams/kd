## 0. Зачем

`parse` (текст → `Document`) без обратного `serialize` — половина формата. Round-trip нужен любому инструменту читай→меняй→пиши (comfy, RP-тулзы, vault-MCP, паблиш-пайплайны).

Две части, обе **портируемы**:
1. **Сериализация формата** — `Document` ⇄ текст. Чистая, ноль deps. **Реализована.**
2. **Сериализация по схеме** — объект ⇄ `Document` через JSON Schema + `x-storage`. Схема = `.json` (кроссплатформенна). **К реализации.**

**Принцип портируемости (исправляет §11 engine-spec):** граница НЕ «read портируем / write TS-only». Граница — **поведение портируемо / статическая типизация TS-only.** При актуализации engine-spec перенести туда.

**Первый потребитель §3:** паблиш-тулзы площадки карточек — JSON с wire ⇄ карточка как `.mdd` на диске. Схемы уже существуют (стандарт nr-schema).

## 1. Сериализация формата (без схемы) — РЕАЛИЗОВАНО

### 1.1 API

```ts
function serialize(doc: Document, opts?: SerializeOptions): string

interface SerializeOptions {
  sigil?: Sigil            // '$' (mdz) | '@' (mdd). По умолчанию — doc.sigil
  baseLevel?: number       // уровень корневых блоков, по умолчанию 1
  eol?: '\n' | '\r\n'      // по умолчанию '\n'
}
```

### 1.2 Контракт: round-trip

```
parse(serialize(doc)) ≡ doc          (семантически идентичный Document)
serialize(parse(text)) ≈ text        (канонически идентичный текст — 1.4)
```

### 1.3 Правила вывода (зеркало format-spec)

**Блоки (§2.1):** `'#'.repeat(L+baseLevel-1) + ' ' + sigil + name + (id ? ' ' + id : '')`, вложенные рекурсивно.
**Атрибуты (§2.2):** `sigil + key + ': ' + serializeValue(value)`. Точка в ключе — литерал, не разбивается.
**Тело (§2.3):** после атрибутов, как есть.
**Значения:** скаляр string — с обратным эскейпингом (1.5) или в кавычках (когда bare-вывод изменил бы значение); number/boolean/null — канонично; список — `sigil[...]`, элементы со спецсимволами в кавычках; `InterpolatedValue` — восстановление raw, opt-out `\${` из текстового сегмента (nr-parts); tbl — §2.

### 1.4 Канонизация

Канонический вид: один пробел после `:`, порядок из `Document`, минимальный достаточный эскейпинг, eol по опции. Побайтный round-trip исходника (комментарии, форматирование) — НЕ цель ядра, это редактор поверх (vault-MCP).

### 1.5 Обратный эскейпинг

Точное обратное §2.5 format-spec: ведущий сигил → `\$`/`\@`, ведущая `[` → `\[`, литеральный `${` → `\${`, `\` → `\\`. Многострочное значение атрибута невозможно bare → кавычки (`\n`/`\t` эскейпятся внутри кавычек) либо тело.

## 2. tbl сериализация

### 2.1 Вывод — РЕАЛИЗОВАНО

Симметрия §5 format-spec: заголовок + записи построчно, ячейки через ` | `, коэрсия обратно.

**ЗАКРЫТО (пункт 1 v1): ячейка (или имя колонки) с `|` при выводе — в кавычках.** Реализация (`cellNeedsQuote`) и была кандидатом спеки; реализация = канон. Внесено в format-spec §5 (правка 03.07.2026).

### 2.2 Список скаляров

Вырожденная tbl (одна безымянная колонка) — реализовано.

### 2.3 Типизированный заголовок — К РЕАЛИЗАЦИИ

**Мотивация (owner, 03.07.2026):** десятки уникальных standalone-таблиц (атрибуты генерации персонажей). Внешняя схема 1:1 к каждой = два файла, файл не самодостаточен. Легаси `.tbl` (старый `core/tbl`) нёс типы в файле — свойство переносится в новый tbl как опциональная аннотация колонки.

**Синтаксис заголовка:**

```
name | weight:number | tags:list(;) | rare:boolean!
```

- `имя[:тип][!]` — аннотация опциональна. Без неё — текущее поведение (per-cell коэрсия §3 format-spec). **Обратная совместимость полная: существующие tbl не меняют поведения.**
- Типы (закрытый набор v1): `string`, `number`, `boolean`, `list(<sep>)` — список-в-ячейке с разделителем (один символ; замена легаси strList). Легаси `text` не переносится: длинный текст в mdd живёт в теле, не в ячейке.
- `!` — required: пустая ячейка в этой колонке = ошибка парса таблицы.
- Типизированная колонка **однородна**: каждая ячейка коэрсится к объявленному типу; невозможная коэрсия (`abc` в `number`) = ошибка, не молчаливая строка.
- Литеральное `:` в имени колонки — эскейп `\:` (либо имя в кавычках, тогда весь квотед — имя, аннотации нет). При выводе имя с `:` эмитится с `\:`.
- Приоритет источников типов: **внешняя схема > инлайн-типы заголовка > per-cell коэрсия.** Схема побеждает потому что несёт внешний контракт; конфликт схемы и инлайн-типов — предупреждение, действует схема.
- Типизированный заголовок = встроенная микро-схема: из него механически выводится JSON Schema фрагмент (`weight:number` → `{"type":"number"}`, `!` → required, `list(;)` → `{"type":"array", "x-mdd":{"separator":";"}}`). Экспорт-хелпер: `tableSchema(block): JSONSchema` — производная, не хранится.

**Serialize:** типизированный заголовок round-trip'ится как есть (аннотации — часть заголовка); ячейка `list` сериализуется join по разделителю; ячейка со значением, содержащим разделитель колонки или свой list-разделитель — в кавычках.

Нормативный текст — также в format-spec §5.4 (правка 03.07.2026); при расхождении format-spec главнее.

## 3. Система типов / схема — К РЕАЛИЗАЦИИ

### 3.1 Модель

- **Схема = JSON Schema 2020-12** + extensions (`x-storage`, `x-mdd`, `x-ui`) — **по стандарту nr-schema**, он источник истины по вопросам «что такое схема, где канон, как авторится»:
  - канон — `schemas/*.json`;
  - способ производства — режим уровня meta.mdz (typebox / imported / json), ядру безразличен;
  - ядро §3 ест схему как plain JSON-объект, TypeBox/кодгенов не знает.
  *(ЗАКРЫТО: формулировка v1 «источник истины: TS-тип → кодген» устарела — перерешена стандартом nr-schema 02.07.2026. Спека §3 собственной версии этого решения не несёт.)*
- **Схема навешивается на ЗАПИСЬ (блок), НЕ на документ.** Документ — лента/снимок, блок — типизируемая структура.

### 3.2 x-extensions

**`x-storage`** — контракт сериализации (ПОРТИРУЕМО): куда поле кладётся. Значения: `attr` (по умолчанию) | `body` | `name` (имя блока) | `id` (id блока). Семантика name/id — как в blockCast: name = имя (`provider`), id = идентификатор экземпляра (`openrouter`).

**`x-mdd`** — уточнения представления (ПОРТИРУЕМО). **ЗАКРЫТО (пункт 2 v1), набор v1:**
- `list`: `flow` (литерал `@[...]` в атрибуте) | `tbl` (тело-таблица) | `lines` (тело построчно) | `blocks` (повторяющиеся блоки —, §3.5);
- `separator`: разделитель для списка-в-ячейке (согласован с `list(<sep>)` заголовка §2.3);
- `unknown: 'block'` — catch-all неизвестных полей на уровне объекта (§3.6).
Расширение набора — по потребителю, не впрок. Для `list: tbl` типы колонок берутся из `items.properties` схемы (богаче легаси-типов: enum, pattern, min/max).

**`x-ui`** — рефлексия/UI (TS-only, порты игнорируют). **В сериализацию не входит** (см. 3.3).

```jsonc
{
  "type": "object",
  "properties": {
    "description": { "type": "string", "x-storage": "body" },
    "model":       { "type": "string" },                          // attr по умолчанию
    "tags":        { "type": "array", "x-mdd": { "list": "flow" } },
    "loras":       { "type": "array", "x-mdd": { "list": "tbl" },
                     "items": { "type": "object", "properties": {
                       "name": { "type": "string" },
                       "sm":   { "type": "number" } } } }
  }
}
```

### 3.3 Сериализация по схеме

```ts
function serializeWithSchema(obj: unknown, schema: JSONSchema, opts?: SchemaSerializeOptions): string
function parseWithSchema<T = unknown>(text: string, schema: JSONSchema, opts?: ParseOptions): T
```

- `serializeWithSchema`: объект + схема → `Document` (раскладка по `x-storage`) → `serialize` (§1).
- `parseWithSchema`: текст → `Document` → сборка объекта по `x-storage` обратно + **коэрсия по типам схемы (тип схемы главнее YAML-коэрсии** — §5 format-spec).
- **ЗАКРЫТО (пункт 3 v1): порядок полей при `serializeWithSchema` = порядок `properties` схемы.** Детерминизм по построению (принцип нулевого диффа nr-schema); схема — единственное место, где порядок решается. `x-ui.order` на сериализацию не влияет — это слой property-grid. `serialize` (§1) как был — порядок Document.
- Поля без `x-storage` → attr. Поле `undefined` — не эмитится; `null` — эмитится как `null`.
- Оба портируемы (схема — данные, раскладка — алгоритм).

### 3.4 Валидация

```ts
function validate(obj: unknown, schema: JSONSchema): ValidationResult
```

**ЗАКРЫТО (пункт 4 v1): Ajv — optional peer.** Решено кейсом nr-schema: ядро зависимости не тащит. TS-делегат: Ajv2020 + `addVocabulary(['x-storage','x-mdd','x-ui'])` (иначе strict-режим падает на x-ключах — правило стандарта nr-schema §5). Ajv не установлен → понятная ошибка «install ajv or provide validator» (инъекция своего валидатора через opts — допустима). Порты берут нативный валидатор своего языка. Свой валидатор не пишем.

### 3.5 `list: blocks` — массив объектов ⇄ повторяющиеся блоки

Главная идиома mdd: гритинги, лорбук-энтри, персонажи. `tbl` (плоская таблица) остаётся дефолтом для массива объектов — `blocks` включается ТОЛЬКО явным `x-mdd: { list: 'blocks' }`, существующие схемы не меняют раскладку.

- **Сериализация:** имя блока = property key **как есть** (singular не выводим). Каждый элемент массива → отдельный дочерний блок с этим именем; внутри элемента `items`-схема работает как обычный объект (`x-storage` attr/body/name/id, вложенность рекурсивна).
- **Парсинг:** собираются ВСЕ children с этим именем (не первый).

```
## $greetings
Hello there!
## $greetings
Oh, hi.
```

**Уточнение (исполнитель):** если `items` несёт поле с `x-storage: name`, имя элемента вытесняет имя-ключ в заголовке блока (`## $alice`), и парсинг собирает элементы как «все блоки, не разобранные другими полями схемы». Отсюда ограничение: такой массив в объекте может быть только один и он несовместим с catch-all (§3.6) — он забирает то, что забрал бы catch-all.

### 3.6 Catch-all: round-trip неизвестных полей

Опция уровня объекта `x-mdd: { unknown: 'block' }`. Без неё поведение прежнее — не описанное схемой молча теряется.

- **Парсинг:** атрибуты и блоки, не покрытые `properties`, собираются в поле результата `$unknown` (константа `UNKNOWN_KEY`, экспортируется).
- **Сериализация:** содержимое `$unknown` эмитится обратно; собственные ключи объекта вне схемы тоже подхватываются (ничего не теряется).
- Скаляр → атрибут; объект/массив (произвольный JSON, `extensions` чужих площадок) → блок с fenced JSON в теле (```` ```json ````) — lossless, opaque. Парс распознаёт fence и возвращает распарсенный объект.
- Ключи, не являющиеся валидными mdd-именами (пробелы, ведущая цифра), не могут стать атрибутом/заголовком → едут одним fenced-JSON блоком `_unknown` (константа `UNKNOWN_OVERFLOW_BLOCK`) + warn.

### 3.7 Map-поля: `patternProperties` → блок с под-блоками

`type: object` + `patternProperties` (или schema-значный `additionalProperties`) **без** `properties` = `Record<string, V>`.

- **Сериализация:** блок = property key; каждый ключ map → под-блок с `name` = ключ; значение → body (скаляр) или атрибуты/блоки (объект, по value-схеме).
- **Парсинг:** все children блока → ключи map.
- Ключ, не являющийся валидным mdd-именем → вся map уезжает fenced JSON в тело блока (lossless) + warn.

```
## $creator_notes_multilingual
### $ru
текст
### $en
text
```

### 3.8 Диагностика

`console.warn` при конфликте типов заменён инжектируемым хуком `opts.warn?: (msg: string) => void` (в `SchemaSerializeOptions` и `ParseWithSchemaOptions`). Дефолт — `console.warn`, поведение по умолчанию не изменилось.

## 7. Приёмка (наблюдаемое поведение)

1. Roundtrip объект → serializeWithSchema → parseWithSchema → deep-equal объект, на реальной схеме карточки (включая body-поле, flow-список, tbl-поле).
2. Повторный serializeWithSchema того же объекта — байт-в-байт (детерминизм).
3. tbl: ячейка с `|` и с `,` в строковом литерале — в кавычках, roundtrip точный.
4. Типизированный заголовок: `weight:number` строка `abc` → ошибка (не строка молча); `rare:boolean!` пустая ячейка → ошибка; `tags:list(;)` → массив; roundtrip заголовка с аннотациями и `\:` точный.
5. Внешняя схема перекрывает инлайн-типы (предупреждение при конфликте).
6. validate: битый объект → список ошибок с путями; без Ajv → ошибка с текстом установки.
7. Существующие 253+ теста nrd-core зелёные (обратная совместимость нетипизированных tbl).

Все изменения аддитивные — дефолты `tbl`/`flow`/`lines` прежние, catch-all и blocks включаются только явным `x-mdd`.

Уточнения, принятые исполнителем и **канонизированные этой записью**:

1. **Дефолт `tbl` для массива объектов теперь виден и на парсинге.** До `listModeOf` при парсинге не знал значения и падал в `flow` — массив объектов без явного `x-mdd.list` сериализовался в `tbl`, но обратно НЕ читался. Режим определяется по `items` (объектная items-схема → `tbl`); симметрия восстановлена, явные режимы не тронуты.
2. **`integer` ≡ `number` при сверке с инлайн-типом заголовка tbl** — колонка `n:number` и схемный `type: integer` конфликтом не считаются (warn не выдаётся).
3. **`InterpolatedValue` в скалярном поле → `.raw`.** Схемный слой работает с данными, не с шаблонами: значение с `${…}` возвращается как исходный текст (было `String(v)` → `"[object Object]"`). Симметрично в `cellToScalar` при сериализации.
4. **Overflow-бэг `_unknown`** (§3.6) и **fenced-JSON fallback для map** (§3.7) — инженерное решение проблемы ключей, невыразимых в mdd-имени. Альтернатива (тихая потеря) противоречит требованию lossless round-trip.

## Реализация —, 14.07.2026

Schema-слой доведён до канона mdd-раскладки Character Card (адаптер карточек — вне ядра). 409 тестов зелёные (391 старых + 18 новых), build чистый. Все изменения **аддитивные и opt-in** — без новых аннотаций поведение прежнее.

### §3.2 `x-storage: 'block'` — поле отдельным блоком

Пятое значение `x-storage` (attr | body | **block** | name | id): поле едет ДОЧЕРНИМ блоком, значение — в теле блока. В отличие от `body` (тело блока-родителя, поле может быть только одно) таких полей у объекта сколько угодно.

Мотивация: проза карточки (`description`, `scenario`, `first_mes`, …) — восемь текстовых полей одного объекта, каждое своим h2-блоком. Иначе они стали бы атрибутами (многострочный текст в кавычках — нечитаемо).

```
## $description
Станционный архивариус.
## $scenario
Смена заканчивается.
```

Пустая строка сохраняется: блок есть, тела нет → парс даёт `''` (не `undefined`).

### §3.5 `list: blocks` для массива СКАЛЯРОВ

 сделал `blocks` для массива объектов. Теперь элемент-скаляр (`items: { type: 'string' }`) → блок с телом-строкой:

```
## $alternate_greetings
Hello there!
## $alternate_greetings
Oh, hi.
```

**Пустой массив** повторяющимися блоками невыразим (ноль блоков = поля нет) — он эмитится вырожденным пустым flow-атрибутом (`$alternate_greetings: $[]`), парс читает его обратно как `[]`. Без этого обязательные пустые списки спеки CC (`group_only_greetings: []`) не переживали бы round-trip.

### §3.6 `unknown: 'inline'` — неизвестные поля собственными ключами

`x-mdd: { unknown: 'block' | 'inline' }`. Сериализация у режимов одинакова (bare-ключи вне схемы подхватывались и раньше), различие — в форме результата ПАРСА:
- `block` — бэг под ключом `$unknown`;
- `inline` — неизвестные поля возвращаются собственными ключами объекта.

Мотивация: канон CC — чужой JSON. Площадки кладут в лорбук-энтри свои поля (`probability`, `selectiveLogic`), и спека CC обязывает их round-trip'ить. С бэгом `$unknown` форма объекта после round-trip'а менялась (`{probability: 100}` → `{$unknown: {probability: 100}}`), и deep-equal с каноном рвался. `inline` даёт round-trip формы 1:1.

### §3.9 `x-mdd: { as: 'json' }` — объявленное opaque-поле

Значение (любой формы) → дочерний блок с fenced JSON в теле. Catch-all умел это для НЕизвестных полей — теперь то же доступно объявленному полю: `extensions` в спеке CC объявлено, но его содержимое — непрозрачный JSON площадок, разбирать его схемой нечем и незачем.

```
## $extensions
```json
{ "site": { "id": 42 } }
```
```

### §3.9 `x-mdd: { block: '<name>' }` — имя блока ≠ ключ свойства

Wire-имя поля и имя блока в документе — разные вещи. Канон карточки: `data` → `# @char <name>`, `entries` → `### @entry <name>`. Без переименования получались бы `# @data` и `### @entries` — документ читается человеком, и имя блока в нём именует СУЩНОСТЬ, а не ключ JSON.

Действует на всех блочных представлениях поля (объект, map, tbl, lines, blocks-элементы) и симметрично на парсе.

### §3.3 `x-mdd: { envelope: true }` — корневой объект без заголовка

У конверта карточки (`spec`, `spec_version`, `data`) нет собственного заголовка: его скаляры — атрибуты корня документа, а единственный блок данных — верхнеуровневый (h1). По умолчанию плоская раскладка корня оставляла h1 «за собой» и эмитила дочерние блоки с h2; `envelope: true` поднимает их на h1.

Результат — канон: `# @char Ирис` (h1), проза h2, лорбук h2, энтри h3. Дефолт (без флага) не изменился.

### §2.1 (format-spec) — кавычки для `id` заголовка

`id` блока несёт имя сущности (имя карточки, имя лорбук-энтри), а имена бывают с хвостовым пробелом (в корпусе карточек — 13 карточек и 19 энтрей) или пустые. Bare-`id` триммится парсером → потеря. Теперь `id`, который bare-выводом изменился бы, эмитится в кавычках (`# @char "Arcadia "`), парс снимает кавычки и разворачивает эскейпы. Обычный `id` (`### @entry city_fall`) — как был, без кавычек.

### Известное ограничение (не баг, а свойство формата)

Тело блока не хранит **ведущие и хвостовые ПУСТЫЕ строки** — они разделители (§2.3). Текст `"Привет.\n\n"` вернётся из round-trip'а как `"Привет."`. Для площадок, чьи данные несут такой хвост, канонизация обязана быть на стороне адаптера (адаптер карточек хранит срезанные пустые строки в мешке площадки и возвращает их при обратной публикации — так держится и mdd round-trip, и zero-diff).
