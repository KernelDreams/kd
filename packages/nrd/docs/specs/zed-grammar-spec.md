# Zed Grammar Spec — nrd (mdd/mdz/message)

**Статус:** черновик 1. Спека под Tree-sitter грамматику для Zed-расширения.
**Опирается на:** `format-spec.md` (грамматика формата), `message-format-spec.md` (сообщения), фактический код парсеров (`src/parser.ts`, `src/splitter.ts`, `src/placeholder.ts`, `src/includes.ts`, `src/value.ts`).
**Цель:** единая грамматика подсветки для форка markdown, покрывающая базовый md + все nrd-конструкции (`$`/`@` sigil, `%role`, `${}`, tbl, flow, includes).
**Дата:** 04.07.2026

---

## 0. Что делаем и на каком стеке

Форк markdown-грамматики Tree-sitter. Наследуем ВСЮ подсветку markdown (заголовки без сигила, списки, bold/italic, ссылки, таблицы GFM, инъекцию кода в ` ```lang ` блоки), СВЕРХУ добавляем nrd-конструкции.

**Единый язык `nrd`.** Один грамматический движок, одно расширение. Файлы: `.md`, `.mdd`, `.mdz`, `.mds`. Да, вешаем и на `.md` — обычные markdown-доки остаются собой (пересечение с nrd-лексикой почти нулевое); если случайный текст попадёт в nrd-конструкцию и покрасится — не смертельно.

**Стек:** Zed extension = `extension.toml` + Tree-sitter грамматика (Rust/C, компилируется в WASM) + `languages/nrd/highlights.scm` + `languages/nrd/injections.scm` (+ `config.toml` языка). Zed использует Tree-sitter query files (`.scm`) для подсветки и инъекций.

**Предупреждение по стеку (не по объёму):** Zed-расширения на Tree-sitter — узкий фреймворк с граблями (формат `extension.toml`, специфика Zed `.scm` capture-имён, сборка WASM-грамматики, инъекция markdown как базового языка, injection в fenced-блоки). Ожидать 1-2 итерации отладки после первой генерации. Это не «много кода», это «редкий стек».

## 1. Два формата под одной грамматикой (ключевой принцип)

mdd (`@`) и mdz (`$`) — **синтаксически идентичны во всём кроме сигила** (format-spec §1). Грамматика их НЕ парсит одновременно как рантайм (рантайм выбирает один sigil на документ через `ParseOptions.sigil`). Но **подсветка ≠ парсинг**: грамматика красит ОБА сигила статически, всегда, в одном файле.

**Смешивание.** В одном файле реально встречаются и `$`-конструкции, и `@`-конструкции (mdz — формат-гость, живёт внутри mdd). Для подсветки это два независимых набора узлов, красятся разными цветами:
- `$`-конструкции → capture-суффикс `.mdz` (условно зелёный)
- `@`-конструкции → capture-суффикс `.mdd` (условно голубой)
- sigil-независимое (`${}`, `%role`, ` ````%type `) → нейтральные capture

Тема Zed красит `.mdz`/`.mdd` capture раздельно. Конкретные цвета — дело темы, грамматика лишь разводит capture-имена.

## 2. Лексика — полный список узлов

Ниже — всё что грамматика должна распознать. Форма для `$` и `@` идентична; пишу через `S` = «сигил формата» (`$` либо `@`), реализуется двумя параллельными правилами с разными capture.

### 2.1 Заголовок-блок

```
## Sname
## Sname id
```

- `#`×N (N=1..6), пробел, сигил `S`, имя.
- Имя: `[A-Za-z_][A-Za-z0-9_.-]*` (точка ЛИТЕРАЛЬНА, часть имени — не путь).
- Опциональный `id` после пробела — произвольный текст до EOL (триммится).
- Capture: `#`-префикс → `@punctuation.special`; сигил+имя → `@keyword.mdz`/`@keyword.mdd`; `id` → `@label`.

**Закрытие блока:**
```
## S       (сигил без имени)
## S@      ($@ или @@ — явное закрытие)
```
- `## $`, `## $@`, `## @`, `## @@` — закрытие, красится как `@keyword.mdz`/`.mdd`.

**НЕ валидно (не красить как блок):**
- `## $$` — конфликт с Obsidian math. НЕ заголовок-блок. Оставить обычному markdown/тексту.
- (для `@`: `## @@` — ВАЛИДНОЕ закрытие, в отличие от `$$`. Асимметрия: `$$` невалиден, `@@` валиден.)

**Обычный markdown-заголовок** (`## Text` без сигила сразу после пробела) — НЕ nrd-блок, красится нативным markdown-заголовком.

### 2.2 Атрибут

```
Skey: value
Sa.b: value
```

- Сигил, ключ (`[A-Za-z_][A-Za-z0-9_.-]*`, точка литеральна), `:`, опциональный пробел, значение до EOL.
- Значение подвергается распознаванию flow (§2.4), `${}` (§2.6), includes (§2.5) — вложенная подсветка внутри значения.
- Capture: сигил+ключ → `@property.mdz`/`@property.mdd`; `:` → `@punctuation.delimiter`; значение → см. коэрсию (§2.7).

**Мета-namespace `nr-*`:** ключи `$nr-body-parser`, `$nr-default-body-parser` и пр. с префиксом `nr-` — мета-атрибуты движка. Можно выделить отдельным capture `@property.builtin` (опционально, если тема различает). Не критично для v1.

**Bare-флаг:** `Skey` без `:` в inline-контексте (`%role $flag`, см. §2.9) → `true`. Capture как property.

### 2.4 Flow-литерал (список)

```
Skey: S[a, b, c]
```

- Триггер — **сигил + `[`** в начале значения (сразу после `: `).
- Разделитель — `,`. Элементы в кавычках `"b, c"` для запятой внутри. Эскейп `\,`.
- Только скаляры, вложенности нет.
- `S[]` — пустой список. `S[a]` — список из одного.
- Capture: `S[` и `]` → `@punctuation.bracket`; `,` → `@punctuation.delimiter`; элементы → по коэрсии (§2.7).
- **`\[`** в начале значения — литеральная скобка, НЕ flow (проза). Не красить как flow.

### 2.5 Файловая ссылка (include)

```
S[[path]]
S[[path#section]]
S[[#section]]
```

- Сигил + `[[` + путь + `]]`. Опциональный `#section`.
- Встречается как строка-директива И внутри значений/тела.
- Capture: `S[[` и `]]` → `@punctuation.special`; путь → `@string.special.path`; `#` + section → `@label`.
- **Эскейп `\S[[`** (`\$[[`) — литерал, не ссылка.

### 2.6 Плейсхолдер `${}`

```
${ path }
${ fn(arg, arg) }
${ a.${b} }
```

- **Sigil-независимый** — ВСЕГДА `$`, работает и в mdd, и в mdz (format-spec §7). Красится нейтрально (НЕ `.mdz`/`.mdd` — это отдельная ось).
- Путь: сегменты через `.`, сегмент = `[A-Za-z_][A-Za-z0-9_-]*` или число (индекс).
- Вызов: `fn(args)`, имя `[A-Za-z_][A-Za-z0-9_-]*`, аргументы — путь / литерал (`"str"`, число, `true`/`false`/`null`) / вложенный `${}`.
- Вложенность: `${a.${b}}`, `${fn(${x})}` — по балансу фигурных скобок.
- Строковые литералы в аргументах: `"..."` с эскейпом `\"`.
- Эскейп точки в сегменте: `\.` → литеральная точка (`${site\.ru}` → имя `site.ru`).
- Capture: `${` и `}` → `@punctuation.special`; имя функции → `@function`; путь-сегменты → `@variable.member`; индексы → `@number`; строковые литералы → `@string`; `.` разделитель → `@punctuation.delimiter`.
- **Эскейп `\${`** — литеральный `${`, НЕ плейсхолдер. Не красить.

Вложенность обязательна к поддержке (рекурсивное правило). Zed Tree-sitter это тянет через рекурсивные rule + injection не нужен (это не другой язык, это тот же nrd).

### 2.7 Коэрсия значений (для подсветки скаляров)

Значение атрибута/элемента flow красится по типу (format-spec §3):
- `true`/`false` → `@boolean`
- `null` → `@constant.builtin`
- целое/дробное (`42`, `-7`, `3.14`) → `@number`
- `"..."` → `@string`
- прочее → `@string` (проза; можно нейтрально `@none` — но `@string` разумно)

Тонкости коэрсии (ведущий `+`, ведущий `0`, версии `1.10`) — это семантика рантайма, для ПОДСВЕТКИ можно упростить: число красим если матчит `-?\d+(\.\d+)?`, иначе строка. Точная коэрсия подсветке не нужна — это визуал, не парсинг данных.

### 2.8 Эскейпы

Красить как escape (`@string.escape`) в значениях/теле:
`\$`, `\@`, `\[`, `\\`, `\n`, `\t`, `\${`, `\$[[` (и `\@[[`), `\.` (в `${}`), `\,` (во flow).
Прочие `\X` — не эскейп формата, оставить как есть.

### 2.9 Сообщения — `%role` и типизированные блоки

(message-format-spec, работает внутри тела блоков или в standalone chat-файлах)

**Маркер роли:**
```
%role
%user $name: Bob $flag
```
- `%` + имя роли (`user`/`assistant`/`system`/`tool_result`/любая строка).
- Опциональные inline-атрибуты после имени: `$key: value` / `$flag` (парсятся как §2.2/bare-флаг, sigil ВСЕГДА `$` в message-контексте).
- Capture: `%` + роль → `@keyword.role` (нейтральный, отдельный capture); inline-атрибуты → как §2.2.
- **Не путать с `%>`**: `parseRoleLine` матчит `/^%(?!>)/` — `%>` НЕ роль (зарезервировано). Не красить `%>` как роль.

**Типизированный контент-блок:**
````
````%type
````%type $key: value
body (opaque)
````
````
- **Четыре** бэктика + `%` + тип (`text`/`thinking`/`tool_use`/`tool_result`/`image`/`summary`/`usage`/`json`/`code`/любой).
- Закрытие — строка ровно из четырёх бэктиков (`^````\s*$`).
- Тело opaque. ВНУТРИ могут быть трёхбэктиковые ` ```lang ` блоки — они body, не структура (per CommonMark: фенс N бэктиков закрывается только N+).
- Capture: ` ````% ` + тип → `@keyword.type` (или `@tag`); inline-атрибуты → §2.2.
- **Инъекция:** тело типизированного блока по возможности НЕ инъектировать (оно opaque для разных типов). Но если тип известен (`tool_use` → json, `code` → по вложенному языку) — опционально. Для v1: тело красить нейтрально, вложенные ` ```lang ` пусть markdown-инъекция обработает если сработает.

### 2.10 tbl — таблицы в теле

(format-spec §5)

```
name                  | weight:number | tags:list(;) | rare:boolean!
zit/pinup.safetensors | 1.0           | a;b;c        | true    // комментарий
```

- Разделитель колонок — `|`.
- **Первая значимая строка — заголовок** (имена колонок).
- Типизированный заголовок (§5.4): ячейка `имя[:тип][!]`.
  - Типы: `string`, `number`, `boolean`, `list(<sep>)`.
  - `!` — required-маркер.
  - Эскейп `\:` для литерального двоеточия в имени.
- `//` — комментарий до EOL.
- Capture: `|` → `@punctuation.delimiter`; имена колонок → `@property`; тип после `:` → `@type`; `!` → `@keyword`; `//` коммент → `@comment`; ячейки-значения → по коэрсии (§2.7).

**Проблема детекции:** tbl vs обычная markdown-таблица (GFM тоже `|`). Отличие: markdown-таблица имеет строку-разделитель `|---|---|` вторым рядом; nrd-tbl её НЕ имеет (вторая строка сразу данные). Грамматике трудно различить статически. **Решение v1:** не пытаться жёстко различать — красить `|`-разделённые строки нейтрально, типизированные заголовки (`:number`, `!`) — единственный надёжный nrd-маркер, его и подсвечивать акцентно. Обычные таблицы пусть идут через GFM-подсветку markdown.

### 2.11 Декоративные строки в теле

(format-spec §6.2) Строки, начинающиеся с `#`, `*`, `` ` ``, `//` внутри тела — декорация (визуальная группировка/отключение).
- `//` в начале строки тела → `@comment`.
- Остальные (`#`/`*`/`` ` ``) — это markdown-конструкции, пусть красятся нативно (заголовок/italic/code). Отдельно как «декорацию» не трогаем — визуально они и так выделены markdown-ом.

## 3. Приоритеты и конфликты

Порядок разрешения при матчинге (важно для Tree-sitter — более специфичное раньше):

1. `## S...` заголовок-блок И `## S`/`## S@` закрытие — раньше обычного md-заголовка.
2. `## $$` — явно НЕ блок (обычный текст/md).
3. ` ````%type ` — раньше обычного ` ```lang ` fenced-блока (4 бэктика раньше 3).
4. `S[[...]]` include — раньше `S[...]` flow (двойная скобка раньше одинарной).
5. `\S...` эскейпы — раньше соответствующих конструкций.
6. `${...}` — независимо от sigil-цвета, во всех значениях/теле.
7. Всё нераспознанное — базовый markdown.

## 4. Highlights capture-имена (сводка)

Разведение `$`/`@` цветов — через суффикс capture. Тема Zed может задать цвета для каждого; если не задаёт — Zed даёт дефолт по базовому имени.

| Конструкция | Capture |
|---|---|
| `$`-заголовок/атрибут/флаг/flow/include-сигил | `*.mdz` суффикс (напр. `@keyword.mdz`, `@property.mdz`) |
| `@`-заголовок/атрибут/флаг/flow/include-сигил | `*.mdd` суффикс |
| `${}` плейсхолдер | нейтрально (`@punctuation.special`, `@function`, `@variable.member`) |
| `%role` | `@keyword.role` (нейтрально) |
| ` ````%type ` | `@keyword.type` / `@tag` |
| скаляры (bool/number/null/string) | стандартные `@boolean`/`@number`/`@constant.builtin`/`@string` |
| эскейпы | `@string.escape` |
| tbl типы | `@type`, required `!` → `@keyword` |
| `//` коммент | `@comment` |

**Решение (принято, помечено):** цвета НЕ хардкодим в грамматике. Грамматика только разводит capture-имена `.mdz`/`.mdd`. Дефолтные цвета (зелёный `$` / голубой `@`) — опционально поставляем как минимальную тему-компаньон в расширении ИЛИ документируем какие capture красить. owner красит под свою тему.

## 5. Injection (`injections.scm`)

- Базовый markdown как язык-основа: наследовать инъекцию кода в ` ```lang ` fenced-блоки (стандартная markdown-инъекция Zed по info-string).
- Тело типизированных ` ````%type ` блоков — для v1 НЕ инъектировать принудительно (opaque). Вложенные ` ```lang ` внутри пусть обработает markdown-инъекция если дотянется.
- Опционально (v2): `tool_use` тело → json-инъекция, `code` тело → инъекция по вложенному языку.

---

## 6. Что НЕ входит в грамматику (границы)

- Резолв `${}`, чтение includes, каскад, коэрсия данных — это рантайм nrd-core, НЕ подсветка. Грамматика только распознаёт лексику.
- Валидация (правильность типов в tbl, существование путей) — не дело подсветки.
- LSP/автокомплит по nrd — вне scope этой спеки (отдельная задача если понадобится).
- Точная коэрсия чисел (ведущий ноль, версии) — упрощаем до regex-матча числа, подсветке точность не нужна.

## 7. Артефакты расширения (что генерит CC)

```
zed-nrd/                        (или встроить в существующий репо-layout)
  extension.toml                — манифест расширения Zed
  grammars/
    nrd/                        — Tree-sitter грамматика
      grammar.js                — определение грамматики (форк markdown + nrd-узлы)
      src/                      — сгенерённый парсер (tree-sitter generate)
  languages/
    nrd/
      config.toml               — конфиг языка (расширения .md/.mdd/.mdz/.mds, ...)
      highlights.scm            — правила подсветки (§4)
      injections.scm            — инъекции (§5)
```

**Развилка для CC — базис грамматики:**
Форк markdown Tree-sitter грамматики — предпочтительно (наследуем md-подсветку + инъекцию кода бесплатно, добавляем nrd-узлы сверху). Альтернатива (грамматика с нуля) — полный контроль, но md-разметку и инъекцию пишем руками, кратно больше работы. **Рекомендация: форк markdown.** Конкретную markdown-грамматику под форк (tree-sitter-markdown, у неё split на block/inline) выбрать на этапе реализации — это решение исполнителя, помечено как открытое для CC.

## 8. Открытые пункты

1. **Базовая md-грамматика для форка** — tree-sitter-markdown (block+inline split) vs другая. Решает CC на этапе реализации.
2. **tbl vs GFM-таблица детекция** — v1 не различаем жёстко, акцент только на типизированные заголовки. Уточнить если мешает на практике.
3. **Инъекция в типизированные блоки** — v1 нейтрально, v2 опционально по типу.
4. **Тема-компаньон** — поставлять ли дефолтные цвета `$`/`@` в расширении, или только документировать capture. Решить с owner после первой рабочей версии.
5. **Название расширения/языка** — принято `nrd`, единый язык на `.md/.mdd/.mdz/.mds`.
