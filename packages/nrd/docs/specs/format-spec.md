# Спека 1 — Формат (mdd / mdz)

**Опирается на:** `core-2.0-architecture-map.md` (v3).
**НЕ описывает:** API движка (IContext/cast/resolve — Спека 2), схему (Спека 3), реализации llm/storage.
**Дата:** 01.06.2026

## 1. Назначение и два формата

Формат — это текстовое представление структурированных данных и конфигов исполнения, нативное для markdown, с прозой первого класса.

Два формата под одним движком:

| | **mdd** | **mdz** |
|---|---|---|
| Назначение | данные (снимок) | конфиг исполнения (лента) |
| Сигил | `@` | `$` |
| Природа | состояние; порядок строк не несёт смысла сверх структуры | лента во времени; повтор ключа = переприсваивание |
| Расширение | `.md` / `.mdd` | `.mdz` |

**Разносигильность (`@` vs `$`) — механизм вложения.** `$` уведён от `@`, чтобы mdz мог жить внутри mdd, внутри шаблонов (handlebars/jinja), внутри чужого текста — не конфликтуя за служебные символы. Следствие: mdz — формат-гость; `$type: llm` посреди `@`-данных делает фрагмент исполнимым.

**Граница mdd/mdz — это точка входа, не документ.** Один и тот же текст — данные ИЛИ программа, в зависимости от того, кто его открыл (аналогия: `.py` — текст, пока не запустил Python). Открыт через рантайм → mdz сверху, исполняется. Открыт как данные → mdd сверху, `$`-конструкции = просто текст.

Грамматика mdd и mdz **идентична** во всём, кроме сигила. Везде ниже, где написано `$`/`@` — подразумевается «сигил формата».

## 2. Лексическая структура

**Кодировка: UTF-8.** Все порты обязаны читать и писать документы в UTF-8. Другие кодировки — вне спеки.

**BOM (добавлено 01.10.2026).** Ведущий `U+FEFF` в начале текста снимается до разбора — парсером и файловым загрузчиком (в т.ч. у включаемых файлов, §2.6). BOM не часть первой строки: иначе он прилипает к ней, и первый атрибут молча перестаёт быть атрибутом. `U+FEFF` не в начале текста — обычный символ. Сериализатор BOM не пишет.

Документ — это последовательность строк (`\n` или `\r\n`; парсер нормализует `\r\n` → `\n`). Строки бывают четырёх видов: **заголовок-блок**, **атрибут**, **тело**, **пустая**.

### 2.1 Заголовок-блок

```
## $name
## $name id
## @name
## @name id
```

- Префикс `#`×N (N=1..6) задаёт **уровень** (h1–h6). Уровень определяет вложенность: блок становится потомком ближайшего предыдущего блока меньшего уровня.
- После `#`-ов — пробел, затем **сигил** (`$`/`@`), затем `name`.
- `name` — тип/имя блока: `[A-Za-z_][A-Za-z0-9_.-]*` (буквы, цифры, `_`, `.`, `-`; точка разрешена — `## @site.ru` валиден).
- Опциональный `id` после пробела — произвольный текст до конца строки (триммится). `id` — **адрес секции для инструментов** (редакторы, vault-MCP), НЕ обязательное свойство данных.
- `id` в кавычках (`# @char "Arcadia "`) — строковый литерал: кавычки снимаются, эскейпы разворачиваются (§3). Так выражается `id`, который bare-выводом потерялся бы: краевые пробелы, пустая строка. Обратно (serialize-spec §1.3) кавычки ставятся ровно в этих случаях — обычный `id` остаётся голым (правка 14.07.2026,: `id` несёт имя сущности — имя карточки/лорбук-энтри, а оно бывает с хвостовым пробелом).

**Коллекции.** Несколько блоков одного `name`:
- без `id` — элементы коллекции по позиции;
- с `id` — элементы коллекции, адресуемые по `id`;
- смешанно (часть с `id`, часть без) — **валидно, коллекция** (не ошибка).

**Закрытие structured-блока.** Закрытие безымянное — возвращает в global-зону любой открытый блок (вид тела на закрытие не влияет). Два эквивалентных синтаксиса:
- `## $@` — явное закрытие.
- `## $` — сокращённая форма (сигил без имени = закрытие).
- Форма `## $@name` зарезервирована на будущее (блок с mdd-телом); закрытие для неё — то же `## $@` / `## $`. В mdz один вид блока: формат тела различается на уровне body-parser, не заголовка.

`## $$` **НЕ валиден** (конфликт с Obsidian-синтаксисом). Для mdd аналогично: `## @` / `## @@`.

`baseLevel` (опция парсера, по умолчанию 1) сдвигает отсчёт уровней: при `baseLevel: 2` корневые блоки — `##`, доступно 5 уровней (h2–h6).

**Про уровни и примеры.** Уровень `#` — неявный корень-контейнер документа (как `{}` в JSON: `# @root` ≈ `"root": {}`). Обычно не пишется: реальные документы начинаются с `##`, потому что `#` — контейнер, а `##` — первые записи (дети корня). Поэтому при дефолтном `baseLevel: 1` примеры в этой спеке используют `##` для записей верхнего уровня — это конвенция, не ошибка. Первый уровень зарезервирован под возможное глобальное пространство имён.

### 2.2 Атрибут

```
$key: value
@key: value
```

- Сигил, `key` (`[A-Za-z_][A-Za-z0-9_.-]*`), `:`, опциональный пробел, `value` до конца строки.
- `value` подвергается коэрсии (§3) и распознаванию flow-литералов (§4) и `${}` (§7).
- Атрибут принадлежит ближайшему предшествующему блоку (или корню, если блока ещё не было).
- **Ключ с точкой** (`$positive.text:`) — одно литеральное имя `positive.text` (точка — часть имени, НЕ путь и НЕ вложенность; вложенность — блоками, §6.3). Парсер сохраняет ключ как есть.

**Точка в ключе атрибута — литеральная часть имени; эскейп НЕ нужен и НЕ применяется.** Имя ключа допускает точку так же, как имя блока (§2.1): `$site.ru: x` → ключ с именем `site.ru` (одно литеральное имя, не путь). Путей в ключах нет — вложенность делается блоками. `\.` на стороне записи ключа не используется. Эскейп нужен только при ДОСТУПЕ из `${}` (§7.1): там точка — разделитель пути, поэтому ключ с точкой адресуется `${site\.ru}`.

**Зарезервированный namespace `nr-*`.** Атрибуты с префиксом `nr-` (`$nr-body-parser`, `$nr-default-body-parser`, `$nr-extends`, `$nr-scope` и т.д.) — **системные директивы формата/движка**, интерпретируются слоями выше, никогда не данные пользователя. Пользовательские ключи не должны начинаться с `nr-`. Конкретный набор мета-атрибутов определяется Спекой 2 и расширяется; здесь фиксируется только резервация префикса.

**Фильтрация — дело потребителя, не движка (C4).** Касты `cast('attrs')`, `cast('keys')` и `get(['nr-x'])` НЕ прячут `nr-*` — данные видны как обычные атрибуты (last-wins, §2.4). Отсекать системные директивы от пользовательских данных — задача слоя-потребителя (тулза/рантайм), а не движка формата.

### 2.3 Тело

Любая строка внутри блока, не являющаяся заголовком/атрибутом/пустой в роли разделителя, — часть **тела** блока. Тело сохраняется как **сырая строка** (с переводами строк, без интерпретации содержимого — см. §6).

Тело и атрибуты могут сосуществовать в одном блоке.

### 2.4 Переприсваивание (только осмысленно в mdz)

Повторный `$key:` — **переприсваивание**, побеждает последний по ленте (last-wins, §8). В mdd повтор семантически не предполагается (снимок), но парсер его не запрещает — разрешение одинаково (last-wins).

### 2.5 Эскейпы

Обратный слеш отменяет служебное значение следующего символа в начале значения/конструкции:
- `\$`, `\@` — литеральный сигил (значение/строка начинается с `$`/`@`, не конструкция).
- `\[` — литеральная `[` (значение-проза начинается со скобки, не flow-литерал).
- `\{` — литеральная `{` в начале значения атрибута: значение целиком в фигурных остаётся строкой, а не JSON5-объектом (§3). Действует только в позиции значения атрибута — там, где живёт JSON5-детекция.
- `\${` — литеральная `${`-последовательность внутри значения (НЕ плейсхолдер; opt-out резолва, см. §7 и Спеку 2).
- `\\` — литеральный обратный слеш.
- `\n` — перевод строки (LF).
- `\t` — табуляция.

**Контекстно-зависимые эскейпы:**
- `\.` — литеральная точка в сегменте пути внутри `${}` (§7.1): `${site\.ru}` адресует имя `site.ru`. В ключах атрибутов (§2.2) точка литеральна сама по себе — эскейп там не нужен и не применяется.
- `\,` — литеральная запятая **только внутри flow-литерала** `@[...]`/`$[...]` (§4). Вне flow не действует — запятая в обычном значении и так не служебная.

Эскейп действует в значениях атрибутов, элементах flow-литералов и теле. `\${` парсер сохраняет нетронутым (НЕ сворачивает в `${`); разворачивает его резолвер финальным проходом — так opt-out держится в значениях и результатах функций, а не только в исходном тексте (Спека 2, §3.1).

Формат НЕ поддерживает других escape-последовательностей: `\r`, `\0`, `\x..`, `\u....` — не распознаются (обратный слеш + символ остаются как есть).



### 2.6 Файловые ссылки

```
$[[path]]
@[[path]]
```

Включение содержимого внешнего файла. Сигил формата + `[[` + путь + `]]`. Парсер **распознаёт** конструкцию и сохраняет как узел-ссылку (аналогично `${}` — §7). Парсер **НЕ** читает файл — чтение делает рантайм через инъектируемый callback (Спека 2).

Семантика включения (инлайн vs context-зона, рекурсия, секции) — Спека 2. Здесь фиксируется только лексика: сигил + `[[` = файловая ссылка, `]]` = закрытие.

Эскейп: `\\[[` — литеральные `[[`, не ссылка.

## 3. Коэрсия значений

Значение без схемы коэрсится по YAML-подобным правилам (самоописываемо). Применяется к значению атрибута и к каждому элементу flow-литерала.

| Вход | Результат |
|---|---|
| `true` / `false` | boolean |
| целое (`42`, `-7`) | number (int) |
| дробное (`3.14`, `-0.5`) | number (float) |
| `"..."` (в кавычках) | string (кавычки сняты, коэрсия НЕ применяется — форсирование строки) |
| `null` | null |
| пусто (после `:` ничего) | пустая строка `""` |
| `{...}` (начинается `{` И кончается `}`) | **JSON5-объект** (только значение атрибута; см. ниже) |
| прочее | string |

Правила:
- **Кавычки форсируют строку:** `$v: "42"` → строка `"42"`, не число. `$v: "true"` → строка.
- **Версиеподобное остаётся строкой:** `1.10` → внимание: по правилу дробного станет `1.1` (number). Если нужна строка `"1.10"` — кавычки обязательны. (Это известная коллизия; решается кавычками.)
- **Ведущий `+` — не знак числа:** `+42` → строка, `+7905551234` (телефон) → строка. Знак числа только `-`.
- **Ведущий ноль + больше одной цифры → строка:** `007` → строка (id/код/версия), не `7`. Одиночный `0` — число. Для дробей ведущий ноль в целой части нормален: `0.5` — число.
- Со схемой (Спека 3) тип поля главнее коэрсии: схема говорит `string` → значение остаётся строкой даже без кавычек.
- Коэрсия — **в портируемом ядре** (одинакова на всех языках; реализуется строковыми примитивами, не regex-диалектами). Исключение — JSON5-объект: грамматика JSON5 заморожена (2018), порт берёт её готовым парсером.

**JSON5-объект как значение атрибута (добавлено 16.07.2026; полная спека — `json5-scalar-spec.md`).**

`$attr: {json5}` — значение атрибута может быть однострочным JSON5-объектом. Детекция **по форме, строгая**: значение (после трима) начинается с `{` И кончается `}` → **обязано** быть валидным однострочным JSON5-объектом; битое → **ошибка парса с номером строки** (`Json5ParseError`), не молчаливый откат в строку.

- Значение с `{`, но без `}` в конце — обычная строка: `$k: {name} says hi` → строка, конфликта с прозой нет.
- Строка целиком в фигурных — эскейп начала: `$k: \{literal}` → строка `{literal}` (§2.5).
- Кавычки главнее детекции (правило «кавычки форсируют строку»): `$k: "{a: 1}"` → строка.
- Только **объект**. Массивы не вводятся — список это flow-литерал `$[...]` (§4). Вложенность внутри JSON5-объекта легитимна (это JSON5, не flow).
- **Многострочное структурное — по-прежнему блоки/тело.** Правило однострочное.
- **Позиция:** только значение атрибута. В элементах flow-литерала (§4) и ячейках tbl (§5) детекция НЕ применяется — там правила §4/§5 без изменений.
- **Каскад атомарен:** JSON5-значение при last-wins (§8) заменяется целиком, deep-merge нет. Гранулярность полей → блочная вложенность.
- **Две точки коэрсии.** Значение без `${}` → объект на parse-time. Значение с `${}` → InterpolatedValue (§7.2), и JSON5-детекция применяется к результату **после резолва** — поэтому `$json: {model: '${model}'}` даёт объект. Точки взаимоисключающие: значение проходит ровно одну, повторная детекция уже коэрснутого значения запрещена (иначе `\{` и кавычки, потреблённые на parse-time, перестают работать).
- **Право на пост-резолвную детекцию — по сырой форме, до резолва.** Детектируется только значение, чей `raw` сам по себе форма `{...}`; такое значение после резолва обязано быть валидным JSON5 (битое → ошибка). Значение, чей raw не форма, **не детектится никогда**, чем бы резолв ни обернулся: `$n: ${x}` при `x="{a: 1}"` → строка, при `x="42"` → строка `"42"`. **Подстановка не меняет тип** — тип даёт форма, написанная автором, а не содержимое переменной. Пост-резолвной коэрсии скаляров нет; асимметрия намеренная.

**Кавычки имеют силу ТОЛЬКО в позиции скаляр-литерала (уточнение, ревью 07.07).** Форсирование строки и снятие кавычек происходят только там, где значение — это скаляр целиком: **значение атрибута полностью** (`$k: "..."`), **элемент flow-литерала** (`$[a, "b, c"]`), **строковый аргумент выражения** (`${fn("lit")}`). В **произвольном тексте и теле** кавычка — обычный символ: `${}` внутри неё резолвится как везде. Поэтому `$json: {"model": "${model}"}` — это интерполяция (значение не является скаляр-литералом целиком, кавычки принадлежат JSON), и `${model}` подставляется. А `$k: "${x}"` (значение — один quoted-скаляр целиком) даёт литерал `${x}`. Резолвер сканирует плейсхолдеры во всём тексте без пропуска quoted-регионов; кавычка остаётся грамматикой только в коэрсии скаляра и в разборе аргументов вызова.

## 4. Flow-литералы списков

Список примитивов в значении:

```
@key: @[a, b, c]      (mdd)
$key: $[a, b, c]      (mdz)
```

- Триггер — **сигил формата + `[`**. Это снимает escape начала: проза со `[` не конфликтует (`@desc: [WIP] foo` — текст, нет сигила перед `[`).
- Разделитель элементов — **запятая**. Внутри скобок действуют правила, как у JSON-массива.
- Элемент с запятой — в кавычках: `@x: @[a, "b, c", d]` → `["a", "b, c", "d"]`. Либо эскейп: `b\,c`.
- Каждый элемент проходит коэрсию (§3): `$[1, 2, true]` → `[1, 2, true]`.
- **Только скаляры.** Вложенные списки/объекты во flow НЕ поддерживаются (для вложенности — секции/тело).
- **Вложенный список — ошибка разбора с позицией** (добавлено 01.10.2026; DECISIONS nr-system 01.10 «Молчаливая порча формата → ошибка»). Признак: разделительная запятая внутри **парной** группы `[...]` — неэкранированной, вне кавычек, вне `${}`. Непарная `[` (ключи вида `[Context:`, одиночная `[`) — текст, как и раньше: у неё одно прочтение. `$k: $[[1,2], x]` → ошибка с позицией (строка, колонка `[`, ключ; смысл: «вложенный список во flow не поддерживается — JSON5-объект или блоки»; в nr-md — `FlowParseError`), а не резка в `['[1', '2]', 'x']`. Скобочная группа **без** запятой внутри — текст скаляра, как раньше: `@[[OOC], abb]` → `["[OOC]", "abb"]`; значение `$[[path]]`, оставшееся нерезолвленным инклудом (§2.6), — та же форма, ошибки нет. Скобки в кавычках (`$["[1,2]", x]`) и экранированные (`\[`) — текст. Сериализатор элементы со `[`/`]` пишет в кавычках — неоднозначного flow он не производит.
- `@[]` — пустой список. `@[a]` — список из одного элемента (НЕ скаляр `a`). `@[...]`/`$[...]` всегда даёт список.
- Литеральная `[` как начало прозы-значения — через `\[`.

**Голая запятая — НЕ список.** `$key: a, b, c` → одна строка `"a, b, c"` (запятая — часть текста/прозы; типичный промпт `man, sitting, chair` — одна строка, не три). Список только явно: flow-литерал, тело блока (§6), либо функция split (Спека 2).

-документе `@[...]` — просто текст, не список. В `@`-документе `$[...]` — просто текст. Гостевой формат лежит инертным текстом до пере-парсинга (например через `cast("mdd")` с другим сигилом). Это следствие принципа §1: точка входа определяет активный формат.

## 5. tbl — таблицы (под-грамматика)

Таблица — тип значения (список структур), записывается в теле блока. Используется, когда элемент списка — структура, а не скаляр (например lora = `{name, strength_model, strength_clip}`).

### 5.1 Синтаксис

```
## $lora
name                    | sm  | sc    // комментарий-заголовок
zit/pinup.safetensors   | 1.0 | 1.0   // pinup
zit/anime.safetensors   | 0.8 | 1.0   // anime
```

- Разделитель колонок — `|`.
- **Первая значимая строка — заголовок** (имена колонок). Каждая последующая значимая строка — запись (строка таблицы).
- Ячейки триммятся, проходят коэрсию (§3).
- Результат: список объектов `[{name, sm, sc}, ...]`; `${lora.name}` адресует поле текущей строки (в контексте перебора — Спека 2).

### 5.2 Комментарии и метки

- `//` — комментарий до конца строки (метка/заметка человека). В заголовке и записях игнорируется парсером таблицы как данные; может использоваться инструментом как label (например имя выходного файла) — но это конвенция потребителя, не данные.
- Декоративные строки (начинающиеся с `#`, `*`, `` ` ``, `//` — см. §6.2) игнорируются. Позволяет визуально группировать/отключать строки.

### 5.3 Список скаляров как вырожденная tbl

Тело без `|` (строка = элемент) — список скаляров (одна безымянная колонка). То есть «список строк» и «таблица структур» — один механизм с разным числом колонок.

> Примечание: §5 описывает синтаксис tbl. Превращение тела в tbl запускается кастом `tbl` (Спека 2) — движок не парсит тело как таблицу, пока клиент не попросит.

---

### 5.4 Типизированный заголовок (добавлено 03.07.2026, serialize-spec v2)

Аннотация колонки в заголовке — опциональная типизация без внешней схемы (самодостаточный файл):

```
name | weight:number | tags:list(;) | rare:boolean!
```

- Синтаксис ячейки заголовка: `имя[:тип][!]`. Без аннотации — поведение прежнее (per-cell коэрсия §3). Обратная совместимость полная.
- Типы (закрытый набор): `string`, `number`, `boolean`, `list(<sep>)` — список-в-ячейке, разделитель — один символ.
- `!` — required: пустая ячейка в колонке = ошибка парса таблицы.
- Типизированная колонка однородна: ячейка, не коэрсящаяся к типу — ошибка, не молчаливая строка.
- Литеральное `:` в имени колонки — эскейп `\:` (или имя в кавычках — тогда аннотации нет). При выводе имя с `:` эмитится с `\:`.
- Приоритет источников типов: внешняя схема (serialize-spec §3) > инлайн-аннотации > per-cell коэрсия.
- Из типизированного заголовка механически выводится JSON Schema фрагмент (`tableSchema`) — производная, в файле не хранится.

### 5.5 Вывод (сериализация; закрыто 03.07.2026)

Ячейка или имя колонки, содержащие `|`, при сериализации берутся в кавычки (parseTable симметрично снимает). Ячейка list-колонки, содержащая свой разделитель — в кавычках. Полные правила вывода — serialize-spec §2.

## 6. Тело как значение

### 6.1 Движок не интерпретирует содержимое тела

Тело блока для движка — **сырая строка** (или коллекция строф). Что эта строка значит — список промптов, `%role`-сообщения, csv, проза, вложенный mdd — **решает клиент через cast** (механизм cast — Спека 2). Стандартные конвенции интерпретации (имена кастов):

- `text` — тело целиком как строка
- `lines` — построчно (массив всех строк, без фильтрации)
- `prompts` — построчно, с игнорированием декоративных строк (`#`, `*`, `` ` ``, `//`)
- `paragraphs` — по пустым строкам (массив абзацев)
- `messages` — `%role`-лента; её разбирает `@kerneldreams/nrd/chat` (Спека 2 §9), не движок формата
- `tbl` — как таблица (§5)
- `mdd` — тело как вложенный mdd-документ (до 6 уровней)

Одно тело — N интерпретаций. Движок отдаёт тело; смысл придаёт клиент.

### 6.2 Декорация в теле

Декорация — **конвенция cast/body-parser, не движка.** Движок отдаёт тело как есть; конкретный каст или body-parser решает, какие строки игнорировать.

Каст `lines` возвращает **все** строки без фильтрации. Касты `prompts` и `tbl` игнорируют декоративные строки — начинающиеся с `#`, `*`, `` ` ``, `//`. Назначение декорации: визуально группировать (`## группа`), отключать (`*элемент*`, `// строка`) элементы, не удаляя их из файла.

Каст `text` возвращает тело **как есть**, включая декоративные строки.

Конкретный набор игнорируемых префиксов — правило каста/body-parser, не движка. Кастомный body-parser может определить свой набор.

### 6.3 Вложенность через тело

Вложенность глубже структуры (§2.1, ≤6 уровней заголовками) уходит в **тело**: тело может нести вложенный mdd (cast `mdd`), JSON, CSV. Каскад (§8) на тело не распространяется — тело разрешается целиком по ключу блока. Это причина, по которой mdz **плоский**: каскад требует плоских ключей, вложенность — в тело.

Ограничение глубины при cast `mdd` — свойство самого парсера mdd (≤6 уровней заголовками), не отдельный лимит. Рекурсия ограничена естественно.

### 6.4 Кастомные парсеры тела

`$nr-body-parser: <name>` — указывает именованный парсер тела для блока. `$nr-default-body-parser: <name>` — для всех блоков документа (может задаваться слоем стопки, не самим документом). Кастомные парсеры — **escape hatch**: нативная реализация per-язык, **непортируемая**; применять, только когда стандартные касты (§6.1) не покрывают tool-конвенцию. Граница портируемости проходит внутри тулзы (кор-механизмы портируемы, кастомный парсер тела — нет).

## 7. `${}`-конструкции — синтаксис

**Это раздел СИНТАКСИСА. Парсер РАСПОЗНАЁТ конструкции, но НЕ разрешает их** (резолв — Спека 2). Граница: парсер выделяет плейсхолдеры и их структуру в значении; их вычисление — резолвер.

### 7.1 Форма

```
${ EXPR }
```
встречается внутри значения атрибута, элемента flow-литерала, тела.

`EXPR` — одно из:
- **путь:** `a`, `a.b`, `a.b.0` — сегменты через `.`. Сегмент — `[A-Za-z_][A-Za-z0-9_-]*` или **число** (индекс). Сегменты бывают `string | number` (JSON = объект + массив, формат поддерживает оба: число → индекс массива, строка → ключ объекта).
- **вызов:** `fn(arg1, arg2, ...)` — имя функции `[A-Za-z_][A-Za-z0-9_-]*`, аргументы через запятую. Аргумент — путь, литерал (строка в кавычках, число, bool), или вложенный `${...}`.
- **вложенность:** `${a.${b}}`, `${fn(${x})}` — `${}` внутри `EXPR`. Парсер разбирает по балансу скобок (рекурсивный спуск / brace-balanced сканер, НЕ regex).

**Точка в именах блоков и ключей.** Имя блока (§2.1) и ключа атрибута (§2.2) может литерально содержать `.` (`## @site.ru`, `$site.ru:`). Внутри `${}` точка — разделитель пути, поэтому для адресации имени с точкой используется эскейп: `${site\.ru}` → имя `site.ru` (см. §2.5). Без эскейпа `${site.ru}` распарсится как путь `site` → `ru`.

### 7.2 Что парсер делает и не делает

- **Делает:** находит `${...}` в значении/теле, разбирает внутреннюю структуру (путь vs вызов, аргументы, вложенные `${}`), сохраняет как узел-плейсхолдер в дереве. Балансирует скобки. Распознаёт `\${` как литерал (НЕ плейсхолдер).
- **НЕ делает:** не ищет значения по путям, не вызывает функции, не подставляет, не рекурсит результат. Это резолвер (Спека 2).

**Контракт выхода парсера:** значение атрибута/тела на выходе парсера — это либо коэрснутый скаляр/список/**JSON5-объект** (если нет `${}` и нет `\${`), либо InterpolatedValue `{ raw: string, placeholders: Placeholder[] }` с распознанными, но не разрешёнными плейсхолдерами (`Placeholder` несёт raw expr + офсеты в `raw` — in-memory представление для резолвера). Значение с `\${`, но без живых плейсхолдеров, тоже InterpolatedValue (`placeholders: []`, `raw` нетронут) — иначе opt-out теряется (Спека 2, §3.1). Каноническая кросс-язычная сериализация значения для conformance — parts-модель §10.2 (`nr-parts`, без офсетов); офсеты — деталь in-memory, в канон не идут. Парсер останавливается на «распознал», резолвер — на «разрешаю».

**Точка коэрсии после резолва (добавлено 16.07.2026).** Резолв текста — `string → string`: `resolve()` контракт сохраняет. Но **значение атрибута** — позиция коэрсии, и после резолва к нему применяется JSON5-детекция (§3). Поэтому API, отдающий разрешённое значение атрибута, возвращает не только строку: `resolveBlockValue()` → `string | Json5Object`. Только JSON5 — пост-резолвной коэрсии скаляров нет (`${x}` с `x="42"` остаётся строкой).

Право на эту точку определяется **сырой формой значения, до резолва** (§3): InterpolatedValue, чей `raw` сам является формой `{...}`. Результат резолва на право не влияет — `${x}`, вернувший `{a: 1}`, объектом не станет. Тело блока (§6) этой точки не проходит вовсе: детекция — только атрибутный путь.

### 7.3 Файловые ссылки в значениях

`$[[path]]` и `@[[path]]` (§2.6) могут встречаться в значениях атрибутов и теле — наравне с `${}`. Парсер распознаёт их как узлы-ссылки, не разрешает. Резолв (чтение файла, инлайн vs context, рекурсия) — Спека 2.

### 7.4 Управляющая логика — НЕ синтаксис

В грамматике нет if/loop/foreach. Управляющая логика — только функциями (`${if(...)}`, `${map(...)}`) на уровне резолвера (Спека 2). Грамматика заморожена: блоки, атрибуты, тело, flow-литералы, JSON5-объект в значении атрибута (§3, добавлено 16.07.2026 —, явное решение owner), `${getter}`, `${fn()}`, переприсваивание. Расширение — через функции, не через новый синтаксис.

Заморозка означает: правка этого списка — только явным решением, не по ходу реализации. JSON5-объект вошёл как закрытие давнего открытого пункта «flow-map» (§9), а не как новый класс синтаксиса: это по-прежнему значение атрибута, коэрсируемое по форме.

## 8. Каскад

Несколько источников (слоёв) одного документа склеиваются и разрешаются как одна лента.

### 8.1 Механика

**Каскад = конкатенация стопки + last-wins.** Слои склеиваются в порядке приоритета (низший → высший), результат парсится как одна лента. Порядок склейки сам производит каскад оверрайдов — отдельной подсистемы merge/override НЕТ.

Пример стопки (рантайм определяет состав — Спека 2 / рантайм): глобальный конфиг → проектный → документ → аргументы вызова. Верхний слой переприсваивает нижний.

### 8.2 Разрешение по ключу

При склейке:
- **атрибуты:** повтор ключа → last-wins (§2.4).
- **тела блоков:**
  - тип-одиночка (один блок данного `name`) → последнее тело;
  - тип-множество (коллекция) → элементы собираются; при совпадении `id` — last-wins внутри id;
  - (тип + id) → последний с этим id.

### 8.3 Плоскость как следствие

Каскад требует **плоских ключей** (совпадение ключа между слоями для last-wins). Поэтому mdz плоский (§6.3); вложенные данные — в теле, где каскад не действует (тело разрешается целиком, не по-полям).

## 9. Контракт сериализации (портируемый минимум)

Чтобы порты (TS/Python/…) читали значения одинаково, формат фиксирует кодирование значений. Это минимальный слой, обязательный в портируемом ядре (полная схема — Спека 3, опциональна и частью TS-only).

Фиксируется:
- **scalar** — коэрсия §3.
- **list** — flow-литерал §4 (разделитель `,`, кавычки, эскейп). Голая запятая — НЕ список.
- **table** — tbl §5 (разделитель `|`, первая строка — заголовок).
- **map** — однострочный **JSON5-объект** в значении атрибута: `$attr: {json5}` (§3, 16.07.2026). Детекция по форме, строгая; битое → ошибка. Многострочный/гранулярно-каскадируемый map — по-прежнему секциями (блок с атрибутами) или вложенным телом: каскад над JSON5-значением атомарен (§8).
- **разделители** — `,` (список), `|` (таблица), `.` (путь). Все экранируются (`\,`, `\|`) или обходятся кавычками/скобками.

Любые два порта на одном входе обязаны дать идентичный результат по этому контракту (§10).

## 10. Conformance-формат

Языко-нейтральный корпус тестов — клей портов. Каждый тест — пара **вход → ожидаемый результат**.

### 10.1 Форма теста

```
вход:    текст документа (mdd или mdz) + параметры парсера (baseLevel, формат)
выход:   канонический JSON дерева записей (ПОСЛЕ парсинга, ДО резолва)
```

Тестируется **выход парсера** (структура + коэрснутые значения + распознанные, неразрешённые плейсхолдеры). Резолв тестируется отдельно (conformance Спеки 2).

### 10.2 Канонический JSON

- Блоки → объекты/массивы по правилам коллекций (§2.1).
- Атрибуты → поля. Ключ с точкой → одно литеральное поле: `$a.b: 1` → `{ "a.b": 1 }` (не вложенность).
- Значения → коэрснутые (§3); списки → массивы (§4); таблицы при cast `tbl` → массивы объектов.
- Тело → строка под зарезервированным ключом `nr-body`. (Ключ в `nr-*` namespace, не конфликтует с пользовательскими данными.)
- **Интерполированное значение** (текст с `${...}`) → объект `{ "nr-parts": [...] }`. Массив — чередование частей в порядке появления: строка = литеральный текст (verbatim, эскейпы НЕ свёрнуты), объект `{ "ph": "EXPR" }` = плейсхолдер (raw expr, без офсетов). Строгое чередование text/ph/text, пустые text-сегменты на границах допустимы (без особого случая single-ph):
  - `hello ${name}!` → `{ "nr-parts": ["hello ", { "ph": "name" }, "!"] }`
  - `${name}` → `{ "nr-parts": ["", { "ph": "name" }, ""] }`
  - `${fn(${x})} done` → `{ "nr-parts": ["", { "ph": "fn(${x})" }, " done"] }` (вложенный expr — raw, целиком в `ph`)
  - `\${x}` (opt-out, §2.5) → `{ "nr-parts": ["\\${x}"] }` (один text-сегмент, ноль `ph`; эскейп нетронут, разворачивает резолвер)
- Обёртка `nr-parts` обязательна (не голый массив): opt-out-only значение даёт parts из одних text-сегментов (`["\\${x}"]`), неотличимых от flow-списка `["x"]`. Reserved `nr-*` (§2.2) разводит три JSON-типа без коллизий: скаляр → JSON-скаляр, flow-список → JSON-массив, интерполяция → `{ "nr-parts": [...] }`. Порт делит значение на text/ph-сегменты по порядку — без char-офсетов, без кодировочных расхождений между языками.

### 10.3 Обязательность

- TS и Python — обязаны проходить весь корпус.
- C#/PHP — при появлении порта.
- Корпус — единый репозиторий, источник истины наравне с этой спекой. Расхождение реализации с корпусом = баг реализации.

## 11. Слоистые контексты и резолв-конвенции (граница с Спекой 2)

Механика резолва (`resolve`, `IContext`, цепочки) описана Спекой 2. Здесь фиксируются **конвенции**, влияющие на то, как автор пишет документ: скоуп плейсхолдеров, `self`, `$nr-extends`, stdlib. Решения приняты 07.07.2026 («Слоистые контексты»).

### 11.1 Скоуп резолва (C1)

Скоуп резолва = **цепочка, переданная читателем**. Атрибуты блока **НЕ** являются неявным скоупом для плейсхолдеров внутри него.

- Голый `${x}` — **свободная переменная** (параметр): её заполняет читатель из своей цепочки. Набор голых плейсхолдеров документа = его сигнатура-параметры.
- `${self.x}` — **связанная** ссылка на собственную составную единицу (автор-стабильна, см. §11.2).

Дисциплина: `${...}` ходит по цепочке (граница доверия = чей текст резолвится об какую цепочку). Макросы `{{...}}` — отдельный слой (тупой replace с закрытым списком, физически без доступа к цепочке), поэтому не смешиваются с `${}`.

### 11.2 `self` — композитный корень путей (C2)

`${self.x}` — ссылка на составную единицу, в которой текст живёт.

- При чтении контента блока: `self = chainContext(атрибуты блока, $nr-extends-база если есть)`.
- На root-уровне: `self` = сам документ.
- **Композитная семантика (virtual dispatch):** ссылки базы на `${self.x}` видят переопределения наследника — own стоит первым в цепочке, иначе наследование бессмысленно.
- Цикл (`$a: ${self.a}`) ловится существующим cycle-guard резолвера → ошибка.

Реализация: при резолве значения атрибута/тела блока в цепочку подкладывается слой `objectContext({self: <композит>})`; голые переменные проваливаются в reader.

### 11.3 `$nr-extends: <path>` — блочное наследование (C3)

Семантический атрибут (**грамматика НЕ меняется** — это обычный `nr-*` атрибут, §2.2). При построении контекста блока: `chainContext(атрибуты блока, parseDocument(file))` — own-wins, база = дефолты.

- Файл резолвится относительно документа-владельца (путь резолвит инъектируемый загрузчик; ядро остаётся IO-free, как включения §2.6).
- Ленивая загрузка: база читается при первом обращении к ключу, которого нет в блоке. Кэширование — зона загрузчика, не ядра.
- Отсутствующий/битый файл — **ошибка (fail loud)**, не молчаливое игнорирование.
- Цепочки допустимы (база сама может наследовать); цикл `a → b → a` — ошибка.

**Прозрачность лукапа.** Штатная адресация `${block.key}` / `get([block, key])` видит унаследованные значения: own > база. Наследование — свойство ФОРМАТА (живёт в лукапе, как last-wins §8), а не вежливость потребителя: это касается любых блочных данных (пресеты, эндпоинты, ноды, произвольные настройки). Наследование активно, когда документ загружен с ExtendsLoader; без загрузчика `$nr-extends` не резолвится, и обращение к унаследованному ключу — **ошибка (fail loud)**, не молчаливый `undefined`. Своё тело блока бьёт тело базы; блок без тела наследует тело базы (`cast('text')` и производные).

**Диагностика.** `$nr-extends` остаётся ВИДИМЫМ атрибутом (`cast('attrs')`/`keys` его не прячут — правило `nr-*`, §2.2): по документу видно, что блок наследует и откуда. Это важно, потому что наследование невидимо в тексте блока — три написанных атрибута могут читаться как десять.

Третий примитив композиции рядом с `[[include]]` (текст, лексика) и каскадом файлов (слои, §8).

### 11.4 stdlib чистых функций (C5)

Ядро экспортирует `coreFunctions` — реестр **чистых** функций для резолвера (ноль IO; IO живёт в пакете nrd-context, граница доверия = граница пакета):

- `if_else(cond, a, b)` — truthy-ветвление (`false`/`null`/`undefined`/`''` → `b`).
- `not(x)` — отрицание по truthy-конвенции.
- `eq(a, b)` — строгое равенство (`===`, без коэрции типов).
- `default(x, fallback)` — `x === null|undefined` → `fallback`.

Подключаются через `funcContext(coreFunctions)` в цепочку. Аргумент-вызов допускается без обёртки: `${if_else(eq(mode, "a"), 1, 0)}` (вложенный `${}` в аргументах грамматикой поддержан, но избыточен).
